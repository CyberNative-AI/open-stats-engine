# Reading comma-delimited data

`import delimited` and `insheet` read a local CSV into the current dataset. The reader accepts a path with or without `using`. The witnessed options are `clear`, `varnames(1)` (or an abbreviation of `varnames`) for `import delimited`, and `comma` for `insheet`. Other options and import subcommands raise `Unsupported`.

| Behavior | Published log |
| --- | --- |
| `insheet` detects the header and reads comma-separated data with `clear`. It prints the number of variables and observations. The next conversion step refers to lower-case names with dots removed from the original header. | [Dataverse file 6704519, lines 11–12 and 18–34](https://dataverse.harvard.edu/api/access/datafile/6704519) |
| `insheet, comma` reads a quoted path and prints the observation count with grouping. Later text comparisons show a column with a literal `NA` is a string. | [Dataverse file 10521999, lines 9–10 and 32–33](https://dataverse.harvard.edu/api/access/datafile/10521999) |
| `import delimited, varname(1) clear` uses the first record for names. The log gives the automatic encoding message and count, then uses a lower-case name from an upper-case CSV header. | [Dataverse file 7077724, lines 50–52 and 59](https://dataverse.harvard.edu/api/access/datafile/7077724) |
| `import delimited` can detect the header without an option. A later table uses the original upper-case heading for the variable whose command name is lower-case. | [Dataverse file 7241004, lines 10–12 and 27–29](https://dataverse.harvard.edu/api/access/datafile/7241004) |

## Inference rules

- A header supplied by `varnames(1)` is used directly. Otherwise, the first record is a header when it has a nonempty field and all the nonempty fields are nonnumeric. A data record in first position gives the columns names `v1`, `v2` and so on.
- Both commands lowercase names. `insheet` removes punctuation and spaces. `import delimited` replaces those characters with underscores and keeps changed headings as labels. `insheet` keeps a heading as the label when lowercasing was its only change: in the AZEOHU log ([Dataverse file 2753813](https://dataverse.harvard.edu/api/access/datafile/2753813), from [doi:10.7910/DVN/AZEOHU](https://doi.org/10.7910/DVN/AZEOHU)), the one-way frequency table at line 28 is headed at line 31 with the CSV's upper-case heading, not the lower-case variable name. No log shows the label `insheet` gives a heading it stripped of punctuation, so those columns stay unlabelled. Blank names use the column position. Names beginning with digits get an underscore. Names are limited to 32 characters, with a numeric suffix to resolve duplicates and reserved names.
- An all-integer column takes the first storage type that holds it exactly: `byte`, `int`, `long`, then `float` when every value is exact in it and inside the `float` range (magnitude up to about 1.70141173e38; larger `float` encodings are missing values in a `.dta` file), else `double`. A column with any non-integer value takes the session's default type: `float`, rounded to float precision, or `double` after `set type double` (decisions §10). `double` is the nearest binary64 value, which holds 15 to 17 significant digits. Under the default type, decimals beyond the `float` range raise `Unsupported`. Empty fields and the dot missing codes take the engine's numeric missing values. The reader refuses numbers beyond the engine's supported range.
- After choosing the type, the reader compares each integer token with the value that type stores, digit by digit, in any notation. `float` holds every integer up to 2^24 (16,777,216) and `double` every integer up to 2^53. `9007199254740993` and `9.007199254740993e15` are the same integer, and both raise `Unsupported` because binary64 cannot hold the last digit. In a column that also holds a decimal, `16777217` raises `Unsupported` under the default `float` type and reads under `set type double`; `16777218`, which `float` holds, reads under both. `3.5e38` writes two digits, a `double` keeps both, and it reads.
- A column with any nonnumeric token is a string. Its width is the longest value in UTF-8 bytes, with a minimum of one. Empty fields stay empty, and original tokens such as `NA` and `.` stay in string columns. Widths above 2,045 bytes require `strL`, which this reader does not implement.
- The reader recognizes a UTF-8 BOM and reads valid UTF-8. `import delimited` reports ISO-8859-1 for ASCII input without a BOM, or when decoding falls back to Latin-1. Quoted commas, doubled quotes and quoted newlines stay inside the field. Ambiguous record widths and malformed quoting raise `Unsupported`. The reader splits on commas only. Before it splits, it looks for a tab or semicolon outside quoted fields, using the same quoting rules as the split. If it finds one, the file may use that character as its delimiter, so the reader raises `Unsupported` before it makes any column. This covers a tab-separated file with commas inside its fields and a semicolon file with decimal commas. It also refuses a comma file with a bare semicolon in a text field, which the reader cannot tell apart from a semicolon file. A tab or semicolon inside a quoted field reads.

The published logs above show the command forms, counts, some numeric and string uses, and parts of name handling. They contain no immediate storage-type or summary output. The decimal storage rule rests on a downstream witness instead: in PXAPMY models 1 and 12, our reference `zinb` fits fall short of the printed log likelihoods when imported decimals are stored as `double` and generated variables as `float` (decisions §10). That is numerical evidence from local maxima, not a proven bound. The unit tests exercise the engine's chosen storage boundaries, empty fields, and the remaining name rules with invented inputs.
